# Bitcoin Relay Finality and Reorganization Policy

## Confirmation policy

`btc_relay` uses the `Config.min_confirmations` value supplied during initialization (and subsequently managed through `update_config`) as the minimum confirmation depth for an SPV proof. The default configured by the contract test setup is `1`; deployments intended for cross-chain swaps should configure the operational policy required by their risk model. The commonly expected Bitcoin policy is **6 confirmations**, but the contract does not hard-code six confirmations.

A proof is accepted only when its Merkle-proof depth satisfies the configured minimum. A proof below that depth is rejected before the claim is recorded. The relay also validates the block-header length, proof-derived Merkle root, proof-of-work target, and replay status of the transaction ID.

`btc_relay_crypto` contains stateless cryptographic helpers only. It does not maintain Bitcoin chain state or confirmation history.

## Reorganization handling

The current contracts do **not** maintain a Bitcoin header chain, block heights, parent links, competing tips, or a finalized-header checkpoint. Consequently, confirmation depth is an SPV proof-depth admission check, not an on-chain finality guarantee.

After a proof is accepted, the transaction ID is recorded as claimed. That record is intentionally replay-protected and there is no contract entry point that removes it. A later proof for a competing branch is either rejected if its Merkle proof is invalid, or treated as an independent valid claim if it contains a different transaction ID and otherwise satisfies validation. The relay cannot determine from the submitted proof alone that a previously accepted block was reorganized out.

Therefore, a Bitcoin reorganization deeper than the configured confirmation window has the following expected outcome:

1. The relay does not detect the reorganization on-chain.
2. It does not revert, burn, or otherwise roll back the corresponding Stellar-side claim.
3. Existing claimed transaction records remain claimed.
4. Any halt, alert, transaction suspension, or compensating action must be implemented by the off-chain relayer/operations layer (or by an independently governed emergency control), not by `btc_relay` itself.

This is an explicit trust and operational assumption for cross-chain swaps: the configured confirmation depth reduces normal reorganization risk but does not provide cryptographic protection against a reorganization after a claim has been finalized by the relay.

## Test coverage

`test_deep_reorg_does_not_revert_or_halt_claims` submits a proof at the configured six-confirmation threshold and then submits a competing-branch proof at seven confirmations, beyond that threshold. Both valid, distinct transaction IDs are accepted and remain claimed. This documents the current expected response: no automatic reversion, halt, or alert is generated by the contract.
